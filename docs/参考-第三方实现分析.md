# 第三方实现分析：com.x.cnmb

> 2026-11-23。为二期（卫星数量可配 + 参数自然化）做参考，反编译了本机已装的
> `com.x.cnmb`（真实包名 `com.acooldog.toolbox` v2.1.2，26MB，LSPosed 模块，已在系统中启用）。
> 目的是看别人怎么处理"卫星数量"这件事，避免自己闭门设计。

---

## 一、它是什么

| 项 | 值 |
|---|---|
| 包名 | `com.x.cnmb`（伪装）／实际类包 `com.acooldog.toolbox` |
| 版本 | v2.1.2，minSdk 28 / targetSdk 36 |
| 入口类 | `com.acooldog.toolbox.root.RootDiagnosticLsposedModule` |
| 规模 | 单 dex 5.2MB，1915 个类 |
| 在 LSPosed 中 | 已启用，作用域含 `system` |

从类名 `SchoolRunDiag`（校园跑诊断）和它 Hook 的接口看，这个工具的定位是
**针对校园跑类 App 的运行环境伪装**，卫星只是其中一项能力。

---

## 二、它的卫星伪造：一共三招

### 招 1：只改总数，不构造卫星对象

```java
XposedHelpers.findAndHookMethod(GnssStatus.class, "getSatelliteCount", new d());

class d extends XC_MethodHook {
    protected void beforeHookedMethod(MethodHookParam param) {
        if (isModuleActive(LOCATION_NMEA)) {
            param.setResult(activeSettings.l());   // 直接返回配置的数字
        }
    }
}
```

**它没有生成任何一颗卫星的参数**，只是把"总数"这个返回值改掉。

这意味着：**目标 App（校园跑）不会去遍历卫星列表**，只看总数。否则改总量而数组长度不变，`getSvid(i)` 会直接越界崩溃。

### 招 2：往 Location.extras 里塞字段

```java
bundle.putInt("satellites", activeSettings.l());
bundle.putInt("satelliteCount", activeSettings.l());
bundle.putDouble("hdop", activeSettings.i());
bundle.putString("source", "gps");
bundle.putBoolean("mockLocation", false);
```

这解释了之前在本机 `dumpsys location` 里看到的 `{satellites=7, signalQuality=2, source=gps, hdop=1.5}`——
那些 extras 是这类工具塞进去的，不是系统原生字段。

### 招 3：伪造 NMEA 语句

`t0/a.java` 里造了一整套 NMEA：`GPRMC`、`GPGGA`、`GPGSV`、`GPGSA`、`GPVTG`。
其中 `GPGSV` 是卫星明细，每颗带「卫星号, 仰角, 方位角, CN0」四项。

## 三、它的参数生成算法（重点）

```java
// 方位角：每颗固定间隔 30°
private static int a(int i) { return (i * 30) % 360; }

// 仰角：每颗 +7°，取模 80，再加 10 → 落在 10~89
private static int b(int i) { return ((i * 7) % 80) + 10; }

// CN0：按"信号质量"档位，每颗 +3°
private static int c(int i, int q) {
    if (q == 0) return ((i * 3) % 10) + 25;   // 25~34
    if (q == 1) return ((i * 3) % 10) + 35;   // 35~44
    if (q == 2) return ((i * 3) % 10) + 45;   // 45~54
    return 40;
}

// 数量上限：硬性 clamp 到 1~12
public static int n(int i) { return Math.max(1, Math.min(12, i)); }
```

**评价：这套参数是纯线性的。**

- 方位角 `i*30` → 30、60、90… 完美等距
- 仰角 `(i*7)%80+10` → 10、17、24、31… 等差递增
- CN0 `(i*3)%10+base` → 每颗 +3，循环

真实卫星不可能长这样：方位角在球面上是对任意角度分布的，仰角遵循球面均匀分布（低仰角多、天顶少），
CN0 与仰角强相关。它这套只是"数字在合理区间内"，经不起细看。

**而且它的数量上限是 12 颗**，默认 8 颗（`nmea_satellite_count`，存 SharedPreferences，默认 8，clamp 到 1–12）。

## 四、架构差异：它注入 App，我们注入系统框架

| 维度 | `com.x.cnmb` | 本项目 |
|---|---|---|
| 注入位置 | **目标 App 进程**（Hook `LocationManager`、`ConnectivityManager`） | **system_server**（Hook `GnssStatusProvider`、`GnssStatus.writeToParcel`） |
| 生效范围 | 只对勾选作用域的 App 生效 | 所有通过标准 API 读取 GNSS 的 App |
| 需要改的东西 | 每个 App 可能要单独适配（它有 `SchoolRunDiag` 这种专用类） | 一次改源头 |
| 反注入风险 | 高——App 检测到自身被注入会闪退 | 低——不触碰目标 App 进程 |
| 卫星数据完整性 | 只改总数，卫星数组仍是真实的 | 可完整伪造整表 |

本项目的路线更彻底，也更容易过反注入检测。

## 五、对本项目的启示

### 1. 好消息：参数门槛比预想的低

这个工具用等距方位角 + 等差仰角都能正常工作，说明**目标 App 基本不校验参数合理性**，
只看总数是否在某个范围内。所以我们二期做的分布算法（球面均匀、CN0 与仰角相关）
属于"超额完成"，但它不会带来风险，只会更保险。

### 2. 关于"应该有几颗"

| 来源 | 数值 |
|---|---|
| `com.x.cnmb` 默认 | 8（上限硬性 12） |
| 使用者实测真实环境（校园跑显示） | 67，高峰 80+ |
| 差异原因推测 | 该工具默认按「单星座 GPS」的直觉设定；而现代手机多星座合计确实能到 60–80 |

**8 颗在这个工具的语境里"能过"，是因为目标 App 不比较历史、不校验星座构成。**
但如果使用者的 App 显示的是真实 67 颗，那伪造 8 颗就形成了明显落差——
这正是二期要解决的。

### 3. extras 那条路径值得注意

它除了改 `getSatelliteCount`，还往 `Location.extras` 塞 `satellites` / `satelliteCount`。
**有些 App 读 extras 而不读 GnssStatus**。我们的方案只覆盖 `GnssStatus` 路径，
如果目标 App 读 extras，会看到真实值或空值——二期 P2 应当考虑要不要一并伪造这个字段。

### 4. NMEA 路径同理

它造了完整 NMEA。如果有 App 通过 `addNmeaListener` 解析 GSV 取卫星数，我们目前没有覆盖。
这属于潜在缺口，记在这里，视目标 App 的实际行为再决定要不要补。

---

## 六、结论

- 别人的实现比我们简单得多（只改一个返回值），参数质量也明显低于我们的方案
- 它的价值在于提示了两条我们没覆盖的路径：`Location.extras` 与 `NMEA`
- 二期的设计方向不变，但建议 P2 增加一项：**同步伪造 `Location.extras` 里的 satellites 字段**，
  成本很低（改一处 Bundle），覆盖面明显扩大
