## 五、虚拟定位场景：已验证通过（本模块的核心价值）

**2026-11-23 18:59 实测。** 使用者开启虚拟定位（路线模拟）后复测，结果如下。

### 5.1 位置确实被伪造了

| 项 | 开虚拟定位前 | 开虚拟定位后 |
|---|---|---|
| 纬度 | 30.3205130° | **30.3213172°** |
| 经度 | 120.3600130° | **120.3619133°** |
| 高度 | 0.0 m | **56.8 m** |
| 速度 | 0.0 m/s | **2.6 m/s** |
| 方位 | （空） | **63.2°** |

`dumpsys location` 同时确认 `gps provider [mock]` 已接管，屏幕右下角可见「路线模拟中·南2」的悬浮窗。

### 5.2 卫星数没有归零 —— 这正是要验的东西

同一时刻 GPSTest 读数：

```
卫星数量: 8/8/8
CN0: 32.0 / 33.0 / 34.0 / 35.0 / 36.0 / 37.0 / 38.0 / 32.0
仰角: 全 45°    方位角: 0 … 158°    星座: 全 GPS
```

**与未开虚拟定位时逐项一致**，一个数都没变。

### 5.3 一个决定性的旁证

`dumpsys location` 里 mock 位置对象自带的 extras 是这样的：

```
{satellites=7, signalQuality=2, source=gps, hdop=1.5, ...}
```

**虚拟定位模块自己报的是 7 颗，GPSTest 看到的是 8 颗。**

两个数字来源不同：`satellites=7` 走的是 `Location.extras` 这条路径，而 GPSTest 的卫星表来自 `GnssStatus.Listener`。读数显示 8，说明拿到的是本模块伪造的表，而不是 mock 应用塞进去的 7——`onReportSvStatus` / `writeToParcel` 两条钩子确实盖在了 `GnssStatus` 路径上。

### 5.4 结论

| 问题 | 答案 |
|---|---|
| 虚拟定位时卫星数会不会归零 | **不会，仍为 8** |
| 是主动推送接住的，还是序列化拦截接住的 | 两条都在（`hooked3=1` 且 `push` 有时间戳，`hooked2=1` 且 `w2p` 持续刷新） |
| 有没有被第三方定位模块干扰 | 本次无。`com.vincenthzr.locationspoofer` 等模块当时未启用 |

这解决了模块最初要解决的问题：虚拟定位把位置换成假的，卫星数不再是 0，读数看起来像正常室外环境。

## 六、结论

一期四批重构的成果在真机上确认可用，且覆盖了模块的核心使用场景：

- 取值单一数据源（B1）→ CN0/仰角/方位角与设计逐项一致
- 编码纯函数（B2）→ 卫星 ID 1–8 被正确识别为 GPS，`const_ok` 显示真实移位值
- 构建元数据（B3）→ `minSdk 31` 的包在 Android 15 上正常安装运行
- 文档（B4）→ 诊断属性表与实际 `getprop` 输出完全对得上，13 个属性名一个不差
- **核心场景** → 虚拟定位把坐标换掉之后，卫星数仍是 8，且盖过了 mock 应用自己报的 7 颗

**遗留观察（不影响本次结论）**：`GnssStatus.wrap()` 仍是私有 API，本次在这台 Android 15 机器上正常，
但换机型或系统版本可能断裂——这条风险在 `docs/接手记录.md` 里单独留档，等真正遇到再处理。
