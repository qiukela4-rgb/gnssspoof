# 配置界面与参数通道

> 2026-11-23。给模块加了图形界面，点开图标就能调参数，不必再依赖 adb。
> 记录设计、踩到的三个坑，以及最终验证结果。

## 一、界面能做什么

点开桌面上的 **GnssSpoof** 图标：

| 区块 | 内容 |
|---|---|
| **运行状态** | 注入状态、三条通道、编码常量、当前实际颗数、异常摘要；带「刷新」按钮 |
| **启用开关** | 关掉即透传真实卫星数据，用于对照 |
| **数量模式** | 动态波动 / 固定数量 |
| **固定颗数** | 滑块 1–120 |
| **波动区间** | 下限、上限两个滑块；上下限填反会自动纠正 |
| **参与定位** | 滑块 0–80 |
| **按钮** | 保存并应用 / 恢复默认 |

保存后约 3 秒生效，**不需要重启**。

## 二、参数怎么从界面传到 system_server

### 走过的两条路

**第一条（失败）：XSharedPreferences**

模块写 SharedPreferences，system_server 侧用 `XSharedPreferences` 跨进程读。这是 LSPosed 的常规做法。

实测不通。诊断过程：

1. 首次读取拿到空表（`pref_size = 0`），但 `pref_ok` 被提前设成 1，掩盖了失败
2. 修正 `pref_ok` 的时机后才暴露问题
3. 补上清单里的 `xposedsharedprefs` 声明——这是 LSPosed 生成代理文件的前提
4. 重启后代理目录 `/data/misc/apexdata/<uuid>/prefs/com.jiuhu.gnssspoof/` 建出来了，**但里面是空的**
5. 对照组 `me.bingyue.IceCore` 的同名目录里有 `config.xml`（1599 字节），说明这套机制在本机是能工作的

结论：目录建了、文件没复制。受 LSPosed 2.2.1 与 SELinux 策略影响，本地无法进一步定位。
**改用第二条路。**

**第二条（成功）：走 root 写系统属性**

界面点保存时，用 `su -c setprop` 把参数写进系统属性；`system_server` 侧本来就在读属性。

```java
new ProcessBuilder("su", "-c", "setprop persist.gnssspoof.svmin 40; ...")
```

链路：

```
界面滑块 → SharedPreferences（回显用）+ su setprop → 系统属性 → MainHook 读取 → 生成器 → 卫星表
```

首次会弹 KernelSU 授权框，允许一次即可（按包名+签名记录）。

## 三、踩过的三个坑

### 坑 1：`xposedsharedprefs` 声明了也不够

清单里加了 `<meta-data android:name="xposedsharedprefs" android:value="true" />`，
LSPosed 会建代理目录，但本机上没有把 xml 复制进去。**不能只靠声明就假定通道可用**，
必须有可观测的判据（这次是靠 `pref_size` 发现的）。

### 坑 2：`SystemProperties.get` 的双参数版本反射调用失败

原实现：

```java
Method m = sp.getMethod("get", String.class, String.class);
Object raw = m.invoke(null, key, null);   // 传 null 作默认值
```

在 system_server 里这个调用始终失败，异常被 `catch` 吞掉，于是**永远返回默认值**。
后果很隐蔽：配置区间是 40–50，实际产出 64 颗，而 64 落在默认的 58–82 里，
看起来「一切正常」，把缺陷盖住了。

修正：改用单参数版本 `get(String)`，失败返回 null 再取默认值。

```java
Method m = sp.getMethod("get", String.class);
Object raw = m.invoke(null, key);
```

修好之后才第一次真正读到属性。**教训：`catch (Throwable) { return def; }` 会把「读不到」伪装成「用默认值」。**

### 坑 3：`debug.*` 属性重启即失效

Android 只持久化 `persist.*`。原来写 `debug.gnssspoof.*`，每次重启配置归零。

改为写 `persist.gnssspoof.*`；读取顺序为
`persist.gnssspoof.X` → `debug.gnssspoof.X` → 代码默认值。
这样界面保存的配置重启后仍在，adb 临时调参也仍然可用。

## 四、最终验证

### 界面 → 属性

点「保存并应用」后：

```
[persist.gnssspoof.enable]    [1]
[persist.gnssspoof.svmin]     [40]
[persist.gnssspoof.svmax]     [50]
[persist.gnssspoof.fixcount]  [15]
[persist.gnssspoof.svcount]   [0]
```

（`svcount=0` 表示走波动模式）

### 属性 → 钩子

```
debug.gnssspoof.cfg         [40/50/0/15/1/props]
```

格式为「下限/上限/固定数/参与定位/启用/来源」，来源 `props` 表示读的是系统属性。

### 钩子 → 卫星表

GPSTest 读数：**15 / 42 / 42**（参与定位 / 在视野 / 总数）

- 总数 42 落在设定的 40–50 区间
- 参与定位正好 15，等于 `fixcount`
- 五个星座齐（GPS / Galileo / BeiDou / GLONASS），CN0 28.9–46.2 随仰角变化

### 重启后仍然有效

重启设备后 `persist.gnssspoof.*` 全部保留，`cfg` 仍是 `40/50/0/15/1`，颗数 40。

## 五、诊断属性一览（新增）

| 属性 | 含义 | 期望 |
|---|---|---|
| `debug.gnssspoof.cfg` | 钩子最终采用的配置：下限/上限/固定数/参与定位/启用/来源 | `40/50/0/15/1/props` |
| `debug.gnssspoof.pref_size` | 从 SharedPreferences 读到几条键 | 本机恒为 0（通道未通） |
| `debug.gnssspoof.pref_ok` | 是否成功从 SharedPreferences 读到配置 | 本机不出现 |
| `debug.gnssspoof.svcount_live` | 最近一次写入的卫星颗数 | 落在设定区间 |

`cfg` 这一条最有用——它一次说清「钩子到底用了什么参数、从哪读的」，
不用再靠猜。

## 六、已知限制

1. **prefs 通道未通**：`readPrefs` 会每 3 秒尝试一次，始终失败后回退属性。
   留着代码是为了将来 LSPosed 侧修好时能直接用，当前不影响功能。
2. **需要 root**：界面保存依赖 `su`。没有 root 授权时只能读状态、不能改参数。
3. **界面回显读的是 SharedPreferences**：如果用 adb 直接改了 `persist.*` 属性，
   界面上的滑块不会跟着变，需要手动刷新页面重开。
